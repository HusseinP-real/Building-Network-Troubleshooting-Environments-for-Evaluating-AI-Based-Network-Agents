# Benchmark protocol — Ground truth, tickets and evaluation

## Dataset structure

Each fault scenario contains `ground_truth.json` (private evaluator data) and `tickets.json` (agent-facing descriptions). The examples are prewritten and deterministic, not randomly generated by an LLM. All 12 tickets refer to exactly 3 underlying fault states.

## Method

1. Start a fresh lab, allow protocols to converge, verify baseline.
2. Inject one fault; verify fault-related network state and service symptoms.
3. Choose a ticket with a specified reporter type; never include ground truth in the agent prompt.
4. Give SADE a constrained set of observational network tools; log every invocation, output and time.
5. Require structured final output: fault_detected, fault_type, fault_devices, root_cause, repair_suggestion.
6. Score predicted outputs only against withheld ground truth, save model/version, temperature, seed (if available), topology git commit, trial ID and elapsed time.
7. Repair fault, verify recovery, then restart/freshen state for next independent trial.
8. Repeat all reporter conditions multiple times. Report confidence intervals where enough observations exist.

## Prediction JSON schema expected by scoring script

```json
[
  {
    "scenario_id": "F02",
    "ticket_id": "F02_engineer",
    "fault_detected": true,
    "fault_type": "bgp_prefix_withdrawal",
    "fault_devices": ["a1", "a3"],
    "root_cause": "BGP prefix is no longer originated by ISP-A border speakers",
    "elapsed_seconds": 47.2,
    "tool_calls": 12
  }
]
```

Save **real** predictions, then:

```bash
python3 tools/evaluate_agent.py /path/to/real_agent_predictions.json
```

The built-in scorer currently checks fault detection, exact fault type, and exact set of fault devices. `root_cause` is **collected but not automatically semantically graded**. A human adjudicator or a carefully audited normalization rubric is required before asserting root-cause accuracy. `repair_suggestion` is not executed. No SADE implementation is included.

## Required SADE adapter (future work)

The adapter should 1) communicate with the actual SADE installed version, 2) expose read-only commands on running Kathara routers and hosts (e.g. `ip route`, `vtysh -c 'show bgp summary'`, `vtysh -c 'show ip ospf neighbor'`, `ping`), 3) securely constrain command execution, 4) serialize trajectories in structured JSON, and 5) ensure evaluation ground truth is hidden. Do not claim end-to-end integration until real SADE trajectories are saved.

## Experimental analyses to report

- Fault detection / type accuracy / exact device-set localization.
- Diagnostic success by reporter type (general, engineer, expert, misleading).
- Tool calls and elapsed wall-clock time.
- Repeatability across reruns and controlled fault conditions.
- Failure categories (wrong protocol, wrong device, hallucinated root cause, insufficient information).
